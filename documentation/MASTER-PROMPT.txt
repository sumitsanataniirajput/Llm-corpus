6. CRITICAL CUSTOM OTP VERIFICATION SYSTEM

This is one of the most important modules.

Build a dedicated OTP VERIFICATION CENTER inside the Manager App.

The Manager App must control OTP generation, delivery monitoring and verification results automatically through secure backend operations.

No human manager should be required for normal OTP verification.

Complete OTP workflow

STEP 1:

Customer books a ride through the future Customer App.

STEP 2:

The backend creates the booking record.

STEP 3:

The backend calculates and stores the booked route distance.

STEP 4:

After a driver has accepted the booking, the backend generates a cryptographically secure, ride-specific OTP.

STEP 5:

The OTP is securely delivered to the customer's registered phone number through an authorized SMS gateway.

STEP 6:

The Manager App receives the OTP generation and delivery status automatically.

STEP 7:

The customer shares the OTP verbally with the assigned driver.

STEP 8:

The driver opens the OTP screen in the future Driver App.

STEP 9:

The driver sees:

- Booking ID.
- Customer name as permitted.
- Pickup location.
- Destination.
- Booked route distance.
- Estimated fare.
- OTP entry field.
- Distance confirmation field.

STEP 10:

The driver enters the OTP and confirms the booked distance.

STEP 11:

The Driver App sends the OTP, booking identifier and distance confirmation to a secure backend endpoint.

STEP 12:

The backend independently validates:

- Driver authentication.
- Assigned driver identity.
- Ride ownership.
- Booking status.
- OTP hash.
- OTP expiration.
- OTP attempt count.
- Distance confirmation.
- Whether the OTP was already used.
- Whether the ride was cancelled.
- Whether another ride-start operation already occurred.

STEP 13:

If all checks pass, the backend atomically:

- Marks the OTP as verified.
- Records the verification timestamp.
- Changes the ride state to OTP_VERIFIED.
- Records the driver confirmation.
- Authorizes the ride-start transition.

STEP 14:

The Manager App automatically receives the verification result through Supabase Realtime.

STEP 15:

The driver can start the ride only after receiving successful backend authorization.

OTP SECURITY

Mandatory rules:

1. Use cryptographically secure random OTP generation.
2. Store only a secure OTP hash.
3. Never expose OTP values in ordinary admin dashboard logs.
4. Never expose OTP to unauthorized employees.
5. Make OTP unique to the booking.
6. Use configurable expiry, initially five minutes.
7. Allow configurable resend limits.
8. Initially permit a maximum of five incorrect attempts.
9. Apply temporary lockout after repeated failures.
10. Invalidate OTP when the booking is cancelled.
11. Permit submission only by the assigned driver.
12. Prevent replay and duplicate submissions.
13. Use server-side atomic transactions.
14. Never allow the frontend to independently authorize a ride.
15. Record every sensitive operation in audit logs.

Manual OTP operation

Provide two separate capabilities:

A. Manual delivery:

An authorized manager can initiate or retry delivery through the configured SMS provider.

B. Exceptional manual verification:

A separately permission-controlled manager can override a failed verification only under an explicit exceptional procedure, with a mandatory reason, identity confirmation and permanent audit entry.

Never create a universal bypass that any administrator can use without traceability.

BOOKED DISTANCE VS ACTUAL DISTANCE

Store separate values:

- booked_distance_km.
- estimated_route_distance_km.
- actual_distance_km.
- final_billable_distance_km.

The original booked distance must come from the server-generated booking record.

The driver must confirm the displayed booked distance rather than arbitrarily editing it.

If there is a mismatch:

- Block normal verification if required.
- Create a distance discrepancy record.
- Alert the Manager App.
- Allow an authorized correction workflow.
- Preserve the original value.
- Record the corrected value and reason.
- Maintain a full audit trail.

Actual travelled distance must be calculated and stored separately from booked distance.
