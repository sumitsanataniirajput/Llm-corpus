# Database

PostgreSQL on Supabase. 82 tables and 2 views, all in the `public` schema, all with Row Level Security enabled
(an automated test fails if any table is missing it). The exact list of every table and column is in
`documentation/schema-reference.txt` (generated from the real database, not written by hand).

## Conventions

- **Money** is `bigint` paise (`*_paise`). ₹123.45 is stored as `12345`.
- **Multipliers and percentages** are basis points (`*_bp`): `10000` = 1× = 100 %. A 1.5× surge is `15000`; 5 % GST is `500`.
- **Human codes** (`BKG-000123`, `DRV-000045`, `TXN-…`) are generated by the database.
- **Times** are `timestamptz` (stored in UTC, shown in the viewer’s time zone).
- **Errors** raised by functions look like `CODE: message` — the code is stable, the message is for people.
- **Reasons**: sensitive actions require a reason of at least 5 characters.

## Ride status flow

```
BOOKING_CREATED → DRIVER_SEARCHING → DRIVER_ASSIGNED → DRIVER_ACCEPTED → DRIVER_ARRIVING → DRIVER_AT_PICKUP
   → OTP_PENDING → OTP_VERIFIED → RIDE_STARTED → RIDE_COMPLETED → PAYMENT_PENDING → PAYMENT_COMPLETED
Any step before RIDE_STARTED → CANCELLED.        Any ride → DISPUTED → back to its previous status.
```

A trigger rejects any jump that is not on this map, for every user. `RIDE_STARTED` can only be reached through
OTP verification (or a logged manager override).

## How writes are protected

| Kind of table | Who can write |
|---|---|
| Money (payments, refunds, wallets, ledger, payouts), bookings, OTP tables, audit logs, GPS | **Nobody directly.** Only through database functions that check permission, state and idempotency. |
| Drivers, vehicles, customers | Permitted staff may edit profile columns; `status` only through `set_*_status` functions (with reason and audit). |
| Configuration (cities, zones, pricing, coupons, templates…) | Staff with the matching `*.manage` permission, limited to listed columns. |
| Settings | Only through `update_setting()` — keeps the value type and records history. |

## Pricing

A fare uses the newest active rule for the ride’s category whose `effective_from` has passed; a rule for the
pickup’s zone beats a city-wide rule. Fare = base + distance + time + waiting (after free minutes), plus a
time-of-day surcharge (the larger of the night or peak multiplier — they do not stack) plus a surge surcharge
(the larger of the rule’s or the zone’s surge), both calculated on that subtotal. Then the minimum fare is applied,
then the coupon discount, then GST on what remains. Commission is calculated on the fare before discount.
When Google’s route service is not configured, distance is a straight-line estimate and is labelled as such.
The full rule is copied into the booking (`pricing_snapshot`) so later price changes never alter an old ride.

## Scheduled jobs (`supabase/policies/schedule_jobs.sql`)

| Job | When (UTC) | Function |
|---|---|---|
| Housekeeping (expire OTPs, stale GPS alerts, other time-based checks) | every minute | `run_scheduled_jobs()` |
| Daily report | 19:35 (01:05 India time) | `generate_daily_report()` |
| Document expiry warnings | 02:30 | `document_expiry_scan()` |
| Retention clean-up | 21:00 | `apply_retention()` |
| Suspicious-customer detection | hourly at :15 | `detect_suspicious_customers()` |

